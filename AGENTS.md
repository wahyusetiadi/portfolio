# AGENTS.md

# AI Agent Instructions

## 1. Role

You are an AI coding agent working on a personal portfolio website.

Your responsibility is to implement and maintain the portfolio according to:

```text
PRD.md
DESIGN.md
AGENTS.md
```

These documents are authoritative.

When implementing UI, always prioritize:

```text
DESIGN.md
    ↓
PRD.md
    ↓
Existing project architecture
```

---

# 2. Core Mission

The primary goal is:

> Build a portfolio that feels intentionally designed by a human developer/designer, not generated by an AI template.

Every UI decision must support this goal.

---

# 3. Before Changing Code

Before modifying UI:

1. Inspect the existing implementation.
2. Understand existing components.
3. Understand existing styling system.
4. Understand routing.
5. Identify reusable components.
6. Check whether functionality already exists.
7. Avoid rewriting working functionality unnecessarily.

Do not immediately replace the entire project.

---

# 4. Preserve Existing Functionality

Redesign means:

```text
Change presentation
+
Improve UX
+
Improve structure
```

It does not automatically mean:

```text
Rewrite everything
```

Do not break:

* authentication
* APIs
* database integration
* forms
* external integrations
* deployment
* existing routes
* project links
* analytics

unless explicitly required.

---

# 5. UI Implementation Rules

## Rule 1 — No Generic AI UI

Do not generate a standard AI landing page pattern.

Avoid automatically producing:

```text
Gradient hero
↓
3 feature cards
↓
glass cards
↓
statistics
↓
testimonial
↓
CTA
```

unless the content genuinely requires it.

---

# 6. Avoid Decorative Filler

Never add visual elements just because the page looks empty.

Do not automatically add:

* blobs
* glowing circles
* floating shapes
* random icons
* abstract SVG
* animated particles
* gradients
* fake statistics
* badges
* excessive shadows

If the page looks empty, first evaluate:

```text
Content
Typography
Spacing
Layout
```

before adding decoration.

---

# 7. Typography First

When a section does not feel visually strong:

DO NOT immediately add:

```text
gradient
image
animation
icon
background effect
```

First try:

```text
font size
font weight
line height
spacing
alignment
content width
grid structure
```

Typography should carry much of the visual identity.

---

# 8. Cards

Do not turn every section into a card.

Bad pattern:

```text
[ Card ]
[ Card ]
[ Card ]
[ Card ]
[ Card ]
```

Preferred:

```text
Editorial layout
List
Grid
Typography
Whitespace
Selective cards
```

Use cards only when grouping content improves comprehension.

---

# 9. Border Radius

Default:

```text
4px - 12px
```

Do not automatically use:

```text
rounded-3xl
rounded-full
```

for every component.

---

# 10. Color

Use color intentionally.

Accent color should not appear everywhere.

Do not create:

```text
blue gradient
purple gradient
pink gradient
```

just to make the design feel modern.

Neutral space is valuable.

---

# 11. Animation

Before adding an animation ask:

> What UX problem does this animation solve?

If the answer is:

> "It looks cool."

Do not add it.

Prefer:

```text
opacity
transform
small translate
subtle scale
```

Avoid:

```text
infinite animation
large parallax
constant floating
complex physics
```

Respect reduced motion.

---

# 12. Responsive Development

Always implement desktop and mobile together.

Do not finish desktop first and "fix mobile later."

Every UI change must be checked against:

```text
1440px
1280px
1024px
768px
430px
390px
375px
```

Check:

* overflow
* text wrapping
* spacing
* navigation
* image sizing
* buttons
* grid
* typography

---

# 13. Prevent Horizontal Overflow

Never intentionally create horizontal page scrolling.

Be especially careful with:

```css
width: 1200px;
min-width
transform: scale()
absolute positioning
large images
fixed-width components
```

If a preview or canvas requires a fixed internal width, contain it properly so it does not cause page-level horizontal overflow.

---

# 14. Content Rules

Never invent:

* jobs
* clients
* companies
* project results
* statistics
* awards
* testimonials
* technologies

unless they are explicitly provided.

If content is missing, use a clearly identifiable placeholder during development rather than fabricating information.

---

# 15. Copywriting Rules

Do not use generic AI phrases such as:

```text
passionate about technology
turning ideas into reality
innovative solutions
cutting-edge technology
digital experiences
empowering businesses
```

unless the wording is intentionally part of the user's own branding.

Prefer specific language.

---

# 16. Project Showcase

Projects should communicate real work.

Prioritize:

```text
What was built?
Why was it built?
What did I do?
What technology was used?
What was the result?
```

Do not make projects look like generic product cards.

---

# 17. Images

Prefer:

* real project screenshots
* actual UI
* real photography
* meaningful visual assets

Avoid generic stock imagery.

Do not add an image simply because the layout has an empty area.

---

# 18. Component Architecture

Create components when they improve:

* readability
* reuse
* maintainability

Good candidates:

```text
Navbar
Button
ProjectCard
ProjectItem
SectionHeader
ExperienceItem
SocialLink
```

Do not create a component for every small `<div>`.

---

# 19. Existing Design System

Before creating new values, inspect:

```text
CSS variables
Tailwind configuration
theme configuration
UI components
font configuration
spacing tokens
color tokens
```

Reuse existing tokens whenever possible.

Do not create five slightly different versions of the same color.

---

# 20. Dependencies

Do not install a dependency for a small visual effect that can be implemented with existing CSS.

Before installing a package ask:

1. Is it really necessary?
2. Can the existing stack solve this?
3. Does it increase bundle size?
4. Does it introduce security/update concerns?

Prefer native CSS when appropriate.

---

# 21. Accessibility

Every implementation must consider:

```text
Semantic HTML
Keyboard navigation
Focus state
Color contrast
Alt text
ARIA only when necessary
Reduced motion
```

Never remove focus indicators without providing a better accessible alternative.

---

# 22. Performance

Avoid:

* unnecessary client components
* large JavaScript libraries
* unoptimized images
* excessive animation
* unnecessary re-renders
* huge dependencies for simple functionality

Prefer server rendering where appropriate within the existing framework architecture.

---

# 23. SEO

Do not remove existing SEO metadata during redesign.

Check:

```text
title
description
Open Graph
favicon
canonical
semantic headings
```

---

# 24. Code Quality

Code must be:

* readable
* maintainable
* typed where applicable
* consistent with existing project conventions
* free of unnecessary duplication

Do not refactor unrelated code while implementing a design change.

---

# 25. Validation Before Completion

Before declaring a UI task complete:

### Visual

* [ ] Typography hierarchy is clear.
* [ ] Spacing is consistent.
* [ ] Colors are restrained.
* [ ] Cards are not excessive.
* [ ] Decoration is intentional.
* [ ] Website does not look like an AI template.

### Responsive

* [ ] Desktop works.
* [ ] Tablet works.
* [ ] Mobile works.
* [ ] No horizontal overflow.
* [ ] No clipped text.
* [ ] No overlapping elements.

### Technical

* [ ] No console errors.
* [ ] No broken links.
* [ ] No broken routes.
* [ ] No unnecessary dependencies.
* [ ] Existing functionality still works.

### Accessibility

* [ ] Keyboard navigation works.
* [ ] Focus states exist.
* [ ] Contrast is acceptable.
* [ ] Images have meaningful alt text.
* [ ] Reduced motion is respected.

---

# 26. Decision Rule

When there are multiple possible implementations, choose the solution that is:

1. Simpler
2. More intentional
3. More maintainable
4. More accessible
5. More performant
6. More personal
7. Less visually generic

Do not choose an implementation merely because it looks more impressive.

---

# 27. Anti-Pattern Detection

Before submitting UI work, explicitly check:

```text
Does this look like a SaaS landing page?

Does this look like a Tailwind template?

Does this look like an AI-generated portfolio?

Are there too many cards?

Are there too many rounded elements?

Are there too many gradients?

Are there unnecessary animations?

Are there decorative elements without purpose?

Is the copy generic?

Is the design personality missing?
```

If any answer is "yes", revise the implementation.

---

# 28. Final Principle

The agent should follow this principle:

> Make fewer, better design decisions.

A strong portfolio does not need more effects.

It needs:

```text
Strong typography
+
Strong content
+
Strong layout
+
Real work
+
Consistent visual language
+
Good restraint
```

The goal is not to make the website look "more AI modern."

The goal is to make it look **deliberately designed**.
